My initial prompt looked something like this:

```txt
/mattpocock-skills:grill-with-docs This is my plan for Unhurried.

# Main Idea
It is a phone line that doesn't cut off people who stammer. Systems often think they have finished speaking when they haven't, so they are talked over, interrupted or trapped in voice recognition loops. They are also often mistaken their stammering for fraud.

# Deadline and Aim
I need to send this idea for Wednesday 11th November, so I need to create a demo version which works appropriately and does its main functionality: minimise as much as possible people who stutter from being cut off and the system properly understanding their message, without compromising fluent people having to wait for longer. A balance needs to be found.

# Design Idea
My main design idea is:
- Microphone through browser: sounds are recorded and sent to the backend
- Voice Activity Detection: labels each sound as speech or silence
- Endpointer (this will be the most important part of the design): watches the speech-silence pattern and words to decide when the user has actually stopped speaking
- SST: turns audio into text
- Cleanup: removes repetition without changing meaning
- Dialogue: decides the next line (e.g. "what's your account number")
- Response: speaks the reply

# Testing
I will use synthetic testing for intial tests but towards the end, for optimisation, I will use data on real clips from real people who stutter. I found this from Apple's research (SEP-28k speech).

All tests will need a proper evaluation which will be measured using cut-off rate and waiting time (before the system responds).

# Rules
I write the endpointer, completeness and cleanup rules myself and you help with plumbing.
```

## Approaching an Issue

From the skill `to-tickets`, Claude created 10 issue files, which I need to work on one at a time. When I start working with them, I normally have two approaches: 
- Approach A: Core 
- Approach B: Plumbing

When I write code myself, I use Approach A, but when something is a bit more time consuming, I use Approach B.
I have been using these plans for a few of my projects and never had any issues with them. They help me understand my code in a deeper and more technical level.

| | Approach A: Core | Approach B: Plumbing |
| --- | --- | --- |
| **Code Writer** | Me | Claude |
| **Main Skill** | `/tdd` | `/implement` |
| **My job** | I write and debug the logic | It makes the decisions, reads every line and tests it |
| **Claude's job** | Write tests from the cases I give it and also reviews | Write the code and explain it |
| **Reason** | I properly understand the code | Works through code I already understand well enough |

### Approach A: Core

1. In a fresh session `run claude` in the repo and paste the last handoff
2. Plan mode: "We're on ticket issues/00N-*.md. Explain the plan: files, functions, inputs, outputs, tests. No code."
3. /tdd: "I'll write the implementation myself. Write one failing test at a time from my cases, then wait."
4. Red → green → refactor loop: Claude adds a test, and then `run uv run pytest`. If it fails, write the smallest code that passes.
5. I also like Claude to quick me so I understand everything better e.g. "Quiz me with 3 questions, one at a time."
6. `/code-review`: fix real problems and note any suggestion you reject and why.
7. Commit, move the ticket to `issues/done/`, `/handoff` and close the session.

### Approach B: Plumbing

1. In a fresh session, plan mode. Ask which parts are plumbing and which (if any) you should write.
2. `/implement`: "Implement issues/00N-*.md. Keep it minimal. Stop after each file and give me a 5-bullet walkthrough."
3. Then read every file. If anything unclear --> /wait-what or "explain this line by line"
4. Run it for real: tests, typecheck, a real call or a WAV streamed in.
5. Check myself, NOTES.md, commit, /handoff.

### Creating Testing Cases

I was unable to find volunteers for this so I decided to go with synthetic testing, which is described on Ticket 2. I manually created a range of testing data using my own voice, which then Claude added a script to generated different types of audio samples: fluent, stuttered and pauses group.

```
We're on ticket issues/02-. Recordings are done and inside eval/data/recordings/ whcih has 26 piece files and 4 natural pause takes (P_.wav), described in eval/recording_scripts.md. The line list is in eval/data/recordings/lines.csv

Plan for make_data.py:
- fluent group: trim each piece, join with short natural gaps (150-300ms)
- stammered group: Block before the digit/date piece (burst = first 60-150ms of that piece, silence 1-3s fileed with room tone), 3 variants per line, fixed seed.
- pauses group: P_* takes as recorded; true_end_ms = detected speech end
- manifest.csv with columns: file, group, line, slot, transcript, true_end_ms, notes.
- commit 3 demo samples: A1 is flient, stammered and the P_A2 pause take

Update the ticket's design notes with these decisions, explain the plan, no code yet
```

After agreeing on the plan, I used `/implement` to add the new changes.


Also, the room tones became zero plus a 60 dBFS noise floor because the recordings had no room tone
