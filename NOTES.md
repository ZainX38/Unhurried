# Unhurried

## Getting Started

**Starting Project:**
```shell
uv init --package --python 3.12     # v3.12 to ensure compatibility with all libraries used
uv add fastapi "uvicorn[standard]" numpy
uv add --dev pytest
mkdir issues, docs/adr, src/unhurried/endpointer, tests, eval/data, eval/results 
```

Files Created:
- **issues/:** contains issues for each part of the project (written by `/to-spec` and `/to-tickets`)
- **docs/:** contains docs generated by `/grill-with-docs`
- **src/unhurried/endpointer/:** it will have the main logic for the endpointer
- **tests:** it will contain one test file per module
- **eval/data:** test downloads, assets etc.
- **eval/results:** will contain evaluation tables and results

### Step 2: `/grill-with-docs`
- It interviews me one question at a time, and also gives me recommended answers. This helps me and Claude Code to be in the same page in a way as we both have the same understanding of the project. It also checks the plan against the code. 
- As we go, it writes terms into `docs/GLOSSARY.md` and decisions into `docs/adr/`


My initial prompt looked something like this:

```txt
/mattpocock-skills:grill-with-docs This is my plan for Unhurried.

# Main Idea
It is a phone line that doesn't cut off people who stammer. Systems often think they have finished speaking when they haven't, so they are talked over, interrupted or trapped in voice recognition loops. They are also often mistaken their stammering for fraud.

# Deadline and Aim
I need to send this idea for Wednesday 11th November, so I need to create a demo version which works appropriately and does its main functionality: minimise as much as possible people who stutter from being cut off and the system properly understanding their message, without compromising fluent people having to wait for longer. A balance needs to be found.

# Design Idea
My main design idea is:
- Microphone through browser: sounds are recorded and sent to the backend
- Voice Activity Detection: labels each sound as speech or silence
- Endpointer (this will be the most important part of the design): watches the speech-silence pattern and words to decide when the user has actually stopped speaking
- SST: turns audio into text
- Cleanup: removes repetition without changing meaning
- Dialogue: decides the next line (e.g. "what's your account number")
- Response: speaks the reply

# Testing
I will use synthetic testing for intial tests but towards the end, for optimisation, I will use data on real clips from real people who stutter. I found this from Apple's research (SEP-28k speech).

All tests will need a proper evaluation which will be measured using cut-off rate and waiting time (before the system responds).

# Rules
I write the endpointer, completeness and cleanup rules myself and you help with plumbing.
```

From this, a few decisions were made:

| Decision | Suggested by | Why |
| --- | --- | --- |
| Vosk for speech-to-text (ADR 0002) | Claude | At first, I wanted to use a Python library called `faster-whisper` but this wouldn't stream data to the backend, which Vosk does |
| Endpointer as a pure state machine fed timestamped events + Ticks (ADR 0001) | Claude | I wanted the Endpointer to analyse the audios and from that figure out some data, but this would be slow. Claude suggested the Endpointer should never see raw audio and turn it into a pure state machine with no clock of its own, which means times arrive only through event timestamps. This is faster than real time and can process throusands of Turns |
| Three-way completeness per slot; a complete answer can end faster than the baseline | | |
| 5-second ceiling on patience | | |
| Call flow: account number → date of birth → reason, with read-back | Me | This will be the demo flow. It starts from easy (account number), which is predictable to something harder (reason), which is harder to predict, meaning the system must work accurately. This will help me properly test and demo my program |
| At most one re-prompt, then fallback (keypad or simulated agent) | Me | During research, I read that adults who stammer, often fell on audio loops on calls. To prevent this, my system will ask three times max a question, and if it doesn't understand, a fallback keypad will be automatically displayed for the answer |
| Barge-in: if the caller keeps talking, the system stops and treats it as the same turn | Me + Claude | It can happen the system misunderstand a timing and cuts off the user, so in case this happens, I suggested to Claude to make the system stop talking and start again. Claude also suggested to measure how often this happens and account it for the evaluation and cut-off rate stat. This will be one of the final implementations if time allows it. |
| Evaluation on symbolic timelines (1,000 calls per severity group, fixed seed) + Piper synthetic audio for the end-to-end check | Claude | This was Claude's test plan to properly evaluate the system |
| Targets: fluent median wait ≤ 900 ms; stammered cut-off rate < 5% | Me | I suggested Claude to use these two values as an evaluation measurement. With these values, I can measure the actual cost of patience. |

### Step 4: `/to-spec` and `/to-tickets`

The spec puts all the long grilling conversation into an organised place that any fresh Claude session can read. It's basically the conversation saved as a document

The most useful one is `to-ticket`, which breaks the spec into tickets, with one file each inside `issues/` folder. Each issue is a small piece of work with: 
- What to build
- Done when 
- Blocking links
- Type

I find this very useful as I can track my progress, and if I need to ask Claude, I can direct Claude to that issue as it's the right size for a **fresh Claude session which keeps it inside the zone where it works the best in the context window**.
